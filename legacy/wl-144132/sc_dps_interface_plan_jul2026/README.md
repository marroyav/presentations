# SC/DPS interface-plan presentation

Discussion deck for an experienced SC/DPS audience. The central proposal is
that a lifecycle-aware interaction/interlock matrix should be the controlled
source from which dependencies, work packages, acceptance tests, and the
staffed technical schedule are derived.

The companion technical report is
`../../daphne_slow_controls_plan/sc_dps_software_integration_plan.tex`. It
defines the proposed repository collection, DUNE DAQ package boundary,
protobuf/status evolution, starter interaction matrix, parallel workstreams,
governance, release gates, and consortium information request.

The deck deliberately:

- acknowledges existing consortium, subsystem, firmware, DAQ, and controls
  work rather than presenting the proposal as a restart;
- separates local test evidence, source-derived projections, and unresolved
  production questions;
- treats normal Slow Controls behavior and Detector Protection behavior as
  linked but separately owned contracts;
- uses the conditional WIB-power/APA-bias ordering question to show why hidden
  cross-system assumptions need owners and independent protection paths;
- proposes two first vertical slices and a practical development test stand;
- asks for collaboration repository governance, interface owners, SURF
  infrastructure specifications, and representative network/PLC hardware.
- makes explicit what must be managed, the one-board-actor/two-client runtime
  rule, and which implementation lanes can proceed in parallel.

## Evidence basis

Quantitative statements are taken from the July 2026 draft report
`DCE-FD2VD-2026-07-27`, generated by the local
`detector-control-emulator` testbed. They are labelled in the deck as local
tests, source-derived projections, or unresolved production questions.
